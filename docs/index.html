Chapter 01

OlonJS Engine & App Entry Point

App.tsx is the maître d' — it gathers all ingredients (components, schemas, configs) and hands them to OlonJSEngine, which runs the show.

The engine provides routing, the Visual Inspector (/admin), preview mode, and cloud save. As the tenant, you supply four things:

PropWhat it isSource
componentRegistrytype string → React component mapComponentRegistry.tsx
schemasZod validation contractsschemas.ts
siteConfigSite-wide identity & settingssite.json
themeConfigColors, fonts, spacing tokenstheme.json
pagesRecord of slug → section arraysgetFilePages()
The split: you own what the site contains. OlonJS owns how it works. This means zero CMS plumbing for the tenant.
return ( <ThemeProvider> <OlonJSEngine componentRegistry={ComponentRegistry} schemas={SECTION_SCHEMAS} siteConfig={siteConfig} themeConfig={themeConfig} pages={filePages} /> </ThemeProvider> );
Chapter 02

Page & Site Config JSON

All content lives in JSON files under src/data/. The Visual Inspector writes back to these same files — they are the single source of truth.

FilePurposeAnalogy
config/site.jsonGlobal site identityBusiness card
config/theme.jsonDesign tokensInterior design spec
config/menu.jsonNavigation linksEntrance signage
pages/*.jsonPer-page section arraysStage direction scripts

Each page JSON is an ordered array of sections. Each section has a type string (resolved via ComponentRegistry), a data object, and optional settings.

{ "sections": [ { "type": "editorial-hero", "data": { "headline": "Welcome to Radice" } }, { "type": "awards-accolades", "data": { "title": "Our Recognition", "awards": [...] } } ] }
Adding a page: drop a new .json file into src/data/pages/. getFilePages() picks it up automatically. No changes to App.tsx needed.
Chapter 03

Capsule (Section Component)

A Capsule is a self-contained LEGO brick: one folder, four files, one job. Every section on every page is a Capsule.

View.tsx
Renders the HTML. Receives typed data and settings props.
schema.ts
Zod contract. Declares required fields and ui:* editor hints.
types.ts
TypeScript types derived from schema via z.infer.
index.ts
Barrel export. Single public entry point for the whole Capsule.

The four files are coupled. Adding a field requires updating schema → types are auto-derived → View uses the new field. Forget schema and the Visual Inspector won't show an editor for it.

To create a Capsule: make the folder, write schema → types → View → index. Then register in ComponentRegistry and schemas.ts. Two lines each.
Chapter 04

ComponentRegistry

The phone book. Maps every "type" string from page JSON to the React component that renders it.

// src/lib/ComponentRegistry.tsx export const ComponentRegistry = { 'header': Header, 'editorial-hero': EditorialHero, 'chef-profile': ChefProfile, 'awards-accolades': AwardsAccolades, 'gallery-grid': GalleryGrid, // ← add one line per Capsule };

A companion file src/lib/schemas.ts uses the same keys to register Zod schemas. Both files must be kept in sync with every Capsule.

FileRegistersPurpose
ComponentRegistry.tsxReact componentWhat to render
schemas.tsZod schemaWhat data is valid
Debug checklist when a section doesn't appear: (1) type string spelled correctly in JSON? (2) registered in ComponentRegistry? (3) schema registered in schemas.ts?
Chapter 05

Zod Schema (Data Contract)

The schema is the customs officer at the door and the Visual Inspector's UI spec — both in one file.

Every schema extends BaseSectionData and adds Capsule-specific fields. The .describe('ui:...') hint drives the editor widget shown in the Visual Inspector.

ChefProfileSchema — field breakdown
namez.string()requiredui:text → single-line input
titlez.string()requiredui:text → single-line input
bioz.string()requiredui:textarea → multi-line
quotez.string().optional()ui:textarea → multi-line
imageImageSelectionSchema.optional()ui:image → image picker
Single source of truth: the schema drives TypeScript types (z.infer) AND the Visual Inspector editor widgets. Write once, both worlds update automatically.
Chapter 06

ThemeProvider (Light/Dark Mode)

One data-theme attribute on <html> switches the entire site. ThemeProvider is wired to localStorage and OS preference.

On first visit it checks: (1) existing data-theme on the DOM, (2) localStorage, (3) prefers-color-scheme. On toggle it writes both the attribute and localStorage atomically via a single useEffect.

useTheme() API
theme'dark' | 'light'current active theme
toggleTheme() => voidflip between modes
setTheme(t: Theme) => voidforce a specific mode
Note: the Header component manages its own local toggle and writes data-theme directly. Both approaches flip the same attribute and produce identical results.
Chapter 07

Local CSS Token Bridge

A four-layer relay race from theme.json to individual pixels. Change the brand color once — every section updates.

1
Engine → :rootWrites global tokens: --primary, --background, …
2
Tailwind @themeMaps tokens to utility classes: bg-primary, text-foreground
3
Capsule <section>Re-maps to --local-bg, --local-text, --local-primary
4
Element utilitiestext-[var(--local-text)] — references nearest ancestor local var
Why --local-*? Isolation: an inverted section (e.g. reservation CTA) just remaps --local-bg: var(--primary) at layer 3 — inner elements need not know. Also: direct DevTools override per section.
Chapter 08

OlonJS Forms

Contact and reservation forms with zero server-side code. Add data-olon-recipient to a <form> and the OlonJS Cloud handles delivery.

PieceRole
FormSubmissionSchemaDeclares fields the form collects (Zod)
data-olon-recipientEmail delivery address on the <form> element
useFormState(id)Returns live status: idle / submitting / success / error
useOlonFormsWired once in App.tsx — intercepts all matching forms
Adding a form: (1) extend schema with WithFormRecipient, (2) add data-olon-recipient attribute, (3) render status via useFormState. useOlonForms auto-detects new forms — no changes to App.tsx.
const { status, message } = useFormState(formId); <form id={formId} data-olon-recipient={data.recipientEmail}> <input name="email" type="email" required /> <button type="submit">Send</button> </form>
Chapter 09

Email Baking Pipeline

A build-time script pre-renders React email templates into static HTML, injecting brand tokens from site.json and theme.json.

Run npx tsx scripts/bake-email.tsx once. Output lands in email-templates/ as complete, self-contained HTML. The OlonJS Cloud uses these as branded shells and injects dynamic form data at send time.

Chapter 10

Admin Middleware (JWT Auth Guard)

Vercel Edge middleware intercepts every /admin request and verifies a short-lived ECDSA JWT before anything reaches the app.

1
Session cookie present?
signature check (no expiry)
2
Bearer token in Authorization header?
full check + expiry
3
Valid Bearer → set session cookie
Max-Age: 1h
4
Neither valid
401 Unauthorized

The private key lives only in the OlonJS Cloud. ADMIN_PUBLIC_KEY in your Vercel env can verify tokens but never create them. JWT verification checks: (1) subject claim admin-access, (2) expiry, (3) ECDSA P-256 signature via crypto.subtle.

Local dev: middleware only activates when VERCEL_ENV is set. Local development is always open — no credentials needed.
